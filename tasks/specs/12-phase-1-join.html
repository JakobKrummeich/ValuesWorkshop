Task 12: Phase 1 — Join

Why now

Checkpoint B is closed and Phase C is groomed. The phase machine walks 1→8 in a live session, but every screen is still a placeholder shell (<h1>Presenter</h1> plus a status banner) — there is no phase switch anywhere in the frontend. Joining already works invisibly: ParticipantHub.OnConnectedAsync runs Session.Join, the roster persists, and the facilitator state carries RosterView(participantIds, participantCount). What is missing is everything a human in the room sees: the QR to scan, their own name on the wall, the roster filling up. Task 12 is the first task that ships a screen a workshop participant would recognise.

Goal

A real screen trio for Phase 1: the presenter shows a large QR of the join URL and the live lobby, the participant lands in a lobby after login, the facilitator watches the roster fill and advances. Ships de+en from the first screen, and puts Playwright into CI.

Solution

  1. Phase routing shell. One per-role map from Phase to component, so Tasks 13–22 slot their screens in instead of rebuilding this. Join is the first entry; every other phase keeps today's shell.
  2. Display names. The participant name comes from the OIDC name claim, captured at hub connect and carried through Session.Join → Roster → ParticipantEntity (+ migration) → RosterView → presenter state. Today no display name exists anywhere in Domain, persistence or wire state, although design/screens.md and design/protocol.md both assume it. WorkshopStateAnonymityTests gets a deliberate, reviewed widening: names are visible in the Phase 1 roster, never in a state that also carries a vote or an answer. A missing or blank claim falls back to a deterministic label instead of crashing.
  3. Presenter join screen. Large QR encoding ${origin}/participant?sessionIdentity=<guid>, the URL in readable text below it, participant count, names appearing live as people join.
  4. Participant lobby. Post-login confirmation: own display name, "waiting for the workshop to start", participant count.
  5. Facilitator join screen. Live roster list plus count, and the existing advance control.
  6. i18n foundation. de+en for every string on these screens and for the shared shells that exist today (AuthGuard, MissingSession, OpenSessionForm, SessionStatusBanner). Language is per-client and switchable, and it must not change the URL — the join URL inside the QR has to stay stable. Existing e2e selectors that assert English text get pinned to a locale.
  7. Playwright in CI. A CI job that builds and starts the compose stack, installs chromium, runs the e2e specs (including the backend-restart reconnect smoke) and uploads the report on failure. Mirrored in scripts/ci-test.sh. This moved up from Task 14 because the reconnect suite is the exact class of defect that only e2e catches, and it is local-only today.

Out of scope

Quiz content and sub-controls (13/14), any screen for a phase ≥ 2, group formation, presenter animation beyond a plain live list, reading the bilingual content JSON (config/*.json is already de+en and is loaded from Task 13 onward), anonymous participants (login stays mandatory), and short session codes — the QR carries the sessionIdentity GUID, as design/domain-model.md already assumes.

Acceptance criteria

  • Scanning the QR (or opening its payload) reaches login and returns to the participant lobby of that exact session
  • A participant joining makes their name appear on presenter and facilitator without reload; the count matches roster size
  • Names round-trip through the store (a restart keeps them) and appear in no state that also carries votes or answers
  • Every string on the three join screens plus the shared shells renders in both de and en; switching language changes neither the URL nor the session
  • The phase map renders the Join screens for Phase 1 and today's shell for every other phase, per role
  • CI runs the Playwright suite and fails the build when an e2e test fails

Slices

  1. i18n foundation + translate the existing shared shells (+ pin e2e selectors)
  2. Playwright job in CI, green on today's 16 tests
  3. Display name end-to-end: claim → Session.Join → entity + migration → RosterView + presenter state, anonymity test widened deliberately
  4. Per-role phase map + participant lobby
  5. Presenter QR + live roster; facilitator roster + advance
  6. Playwright: a participant joins, the name appears on presenter and facilitator

Decisions needed from you

Q1 — i18n mechanism

Option A: an in-house typed dictionary in src/domain/i18n plus a context hook — zero new dependency, choice persisted in a cookie. Option B: next-intl with cookie-based locale (not locale-prefixed routes, which would change the join URL and break the existing e2e URL assertions). Recommendation: A — the string volume is small and it leaves URLs, e2e and the QR payload untouched.

Q2 — Does the presenter screen show names?

design/screens.md says yes, but it widens what the unauthenticated presenter connection may display. Option A: names on presenter and facilitator. Option B: names on facilitator only, presenter shows the count. This is a privacy call, not a technical one. Recommendation: A — the presenter screen is the shared room projection, and people expect to see themselves appear on it.

Q3 — QR generation

Option A: client-side SVG via a maintained dependency (qrcode / react-qr-code). Option B: hand-rolled generator, no dependency. Recommendation: A — QR encoding is spec-heavy and not worth owning; it adds a dependency, so it needs an explicit yes from you.

Q4 — How much e2e runs in CI

The reconnect spec restarts the backend container and budgets 180 s. Option A: run the whole suite in CI. Option B: run everything except the restart spec in CI and keep that one local. Recommendation: A — it is precisely the defect class Task 10 shipped for, and it is worthless if nothing runs it.
