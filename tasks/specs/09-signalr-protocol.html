4. Periodic state resend — self-healing sync

Your requirement: a dropped broadcast must not leave a client stale forever. With a full-state protocol this is cheap to guarantee — just send the latest state again on a timer. Two pieces make it safe and quiet:

1. revision on every state

The session carries a monotonic counter, bumped on every persisted mutation. Every role state record ships it. The client keeps the last revision it applied and drops anything not newer — so a resend of unchanged state costs the UI nothing (no re-render, no flicker), and an out-of-order late arrival can never move the screen backwards.

2. One ticker, per-session, only where it matters

A single hosted background service ticks; per session it resends only when that session has connected clients. The three mapped role states are cached and re-mapped only when revision changes, so a tick between mutations is pure serialization — no repository reads, no domain work, no SQLite traffic.

Honest cost at 500 ms: 2 messages/second/client forever. For 30 phones + laptop + beamer that is ~64 msg/s and a few hundred kB/min of mostly redundant traffic — harmless on a LAN, noticeable on bad conference WiFi (exactly the network where drops happen). Hence the interval question below.

5. What IntentResult is

A hub method is a call, so it can answer the caller privately. That answer is IntentResult: “I accepted it” or “I rejected it, here is the typed reason”. It is not broadcast, it carries no state (state always arrives through the broadcast channel), and it is what lets a phone show “too late — the facilitator already closed this round” instead of silently doing nothing.
