Task 11: Phase state machine

Why now

Task 10 is merged. In the Domain today only invariant I1 (forward-only) exists: PhaseProgress.Advance does CurrentPhase++ and throws past phase 9 — that is the whole state machine. QuizProgress, PresentationWalk and VotingRounds hold their fields but are Restore-only shells with zero transition logic. FacilitatorHub.AdvancePhase sends an anonymous Func<Session,bool> lambda through the pipeline, so WrongPhase, NotAuthorized and MalformedPayload are declared rejection codes that nothing ever produces. The 9-phase list is re-enumerated 8 times across backend and frontend (enum, three JsonDerivedType blocks, three mapper dictionaries, three FE discriminatedUnion schemas) with no test tying the two enums together.

Goal

Make design/state-machine.md executable: forward-only phase walk with exit guards, facilitator-only advance enforced per intent, and the sub-state slots turned into guarded transitions.

Solution

  1. Advance guards. Session.AdvancePhase rejects when the current phase's exit guard fails: 2→3 all questions walked, 6→7 every group Submitted (I12), 7→8 all values shown, 8→9 exactly five winners stand (I15). Typed rejection WrongPhase, distinct from InvariantViolated.
  2. Facilitator-only advance per intent. The advance path checks the actor, not just the connection; a non-facilitator caller gets NotAuthorized.
  3. Sub-state transitions — mechanics, not content. Quiz: PoseNextQuestion / RevealAnswer / ShowLearningText, strictly forward Answering → Revealed → LearningTextShown per question, question count injected rather than hardcoded. Presentation walk: GoToNextValue cursor over group → value. Voting: CloseVoting, StartTiebreakRound bumping RoundNumber. FE ports and screens for these stay with their phase tasks (13, 21, 22/23).
  4. Named intents. Replace the anonymous lambda in FacilitatorHub with named command records routed through IntentPipeline, giving the rejection taxonomy real producers.
  5. Phase-enum parity guard. One test asserting backend Phase and frontend domain/phases.ts agree on names and numbers, killing the silent-drift risk of the 8 re-enumerations.
  6. Persistence. Every new sub-state mutation round-trips through SQLite (columns already exist) under the existing revision check.

Out of scope

Quiz and values content plus tallies (Tasks 13, 15), group work rights (19), solver-driven formation (17/18), vote counting and tiebreak detection (22) — Task 11 hands those tasks the round and cursor mechanics to drive. System entry commands that need computed data (DetermineTopValues, FormGroups, AppointScribes, WinnersDetermined, WorkshopConcluded) stay with their owning tasks; Task 11 only defines the hook where they fire.

Acceptance criteria

  • Non-facilitator advance intent rejected with NotAuthorized, state unchanged
  • Backward transition impossible; past-phase-9 advance rejected
  • Each exit guard has a red-then-green test (blocked, then passing once the guard condition holds)
  • Sub-state transitions unit-tested per phase, including illegal order (reveal before a question is posed, tiebreak while a round is open)
  • Phase-enum parity test fails if backend and frontend diverge
  • Sub-state mutations survive a store round-trip

Slices

  1. Named intent records + per-intent facilitator authorization (NotAuthorized)
  2. Exit guards on AdvancePhase (WrongPhase) + tests
  3. Quiz cursor transitions (question index, reveal, learning text)
  4. Presentation walk cursor
  5. Voting round open / close / tiebreak bump
  6. Phase-enum parity guard + persistence round-trip tests

Decisions needed from you

Q1 — Do the sub-state mechanics belong to Task 11?

Option A (spec's assumption): Task 11 owns the transition mechanics for all three slots, so guards and the rejection taxonomy land once, and Tasks 13/21/22 add only content and tallies. Option B: Task 11 stays at the phase level and each phase task builds its own sub-state machine when it needs it — smaller task now, taxonomy repeated later.

Q2 — Exit guards that need content counts (no spec position)

Guards 2→3 and 7→8 need to know how many questions / values exist, but the content arrives in Tasks 13 and 21. Option A: inject the count into the Domain now (a placeholder count until content exists). Option B: leave 2→3 and 7→8 unguarded in Task 11 — the facilitator may advance freely — and add the guard in the task that supplies the content.

Q3 — Phase parity: test or codegen?

Option A: a test that reads both enums and fails on divergence — cheap, no build coupling. Option B: generate phases.ts from the C# enum at build time — impossible to drift, but adds a codegen step to the frontend build.
